# call_tools vs 官方 PTC `run_code` —— 与 Auto review 的兼容性测试计划（2026-10-03）

背景（哥哥）：检查工具箱插件提供的 PTC 模式跟官方 PTC 有哪些不同，尤其关注它跟**自动授权审查**
（`@deepseek-ai/dsh-experimental-auto-review`，desktop profile 里已开启）之间的兼容性。

---

## 一、先摆事实：两边各是什么

| | 官方 PTC | 工具箱的 PTC 模式 |
|---|---|---|
| 入口工具 | `run_code`（注册表保留名，不能注册、不能顶） | `call_tools`（普通注册工具） |
| 实现在哪 | `deepseek-harness/packages/core/tools/src/ptc.ts` | `dsh-tool-gateway/src/code-tools.js` |
| 程序由谁跑 | `ctx.ptcRuntime` | **同一个** `ctx.ptcRuntime` |
| SDK 段落 | 遍历注册表生成（一百多个工具的签名） | 手写两条声明（`tools.find_tools` / `tools.call_tool`） |
| 子调用调度 | 自己管：有序车道、parallel/exclusive、commit 顺序、日志 append | 不抄 —— 子调用走 `ctx.tools.execute()`（公开执行入口） |
| 何时在场 | `modeFor(scope) !== 'native'` 时由 DSH 挂 | PTC 没开着、且运行时在时才挂（互斥） |
| `mode:'ptc'` 下 | 只有它能被调 | 根本调不到（守卫只放行 `run_code`） |

对齐的部分（gateway 自己声明的）：参数、输出、界面呈现都照 `run_code` 抄；提权语义也是"这一整次程序执行、一次有效"，
两边一致（`ptc.ts:110` 与 `code-tools.js:275`）。

## 二、Auto review 是怎么介入的（关键机制）

读 `packages/experimental/auto-review/src/index.ts` 得到三条硬事实：

1. **第 3-4 行**：`Every native call and every started PTC inner call is reviewed once before its body;
   the outer \`run_code\` transport is deliberately excluded.`
   —— **原生调用全审、PTC 内部调用全审、外层 transport 刻意不审。**
2. **判定 inner call 的依据是 `exec.parent !== undefined`**（第 411 行），然后必须能在会话日志里
   找到对应的 `tool/ptc-dispatch-start`；找不到、或者 callId/name/arguments 对不上，就**抛错**，
   而不是放行：
   - `auto-review: the pending PTC call is missing or ambiguous in the session log`
   - `auto-review: the pending PTC call disagrees with its logged action`
   - `auto-review: the pending PTC binding schema is missing or inconsistent`
   - `auto-review: a PTC call has no owning step in the session log`
3. **拒绝的传播**（README 第 101 行）：PTC 用既有的 inner-call 异常与 catch 行为，
   **被 catch 住的拒绝不强制外层 `run_code` 失败**。

## 三、由此推出的差异与风险（按要紧程度排）

### R1 · 工具箱模式下，每一次元工具调用都要多付一次审查（成本，确定会发生）

`call_tools` 是**普通注册工具**，不是 PTC transport —— 所以在 Auto 下它**本身会被当原生调用审一次**，
它的每个子调用**再各审一次**。`find_tools` / `call_tool` 同理，各审一次。

- 官方 PTC：1 次程序执行 = **N 次** review（N = 子调用数）
- 工具箱：= **1 + N 次**（外层自己也算一次）
- **最刺眼的一条**：工具箱模式的设计初衷是"每次动手前先 `find_tools` 查一下"。
  在 Auto 开着时，**每次检索都是一次完整的模型请求**（README：不缓存、不重试、不截断、不设小输出预算）。
- 判据：跑一次 `find_tools`，数会话日志里 `request/header` 事件多了几条。

### R2 · inner call 与日志的对齐（会不会硬失败）

auto-review 对 PTC inner call 做的是**严格对照**：`subCallId`、name、arguments 三者都要与
`tool/ptc-dispatch-start` 一致。gateway 是**自己造**这些事件的（"机制照搬内置 PTC"）。

已经核对过的两点（代码层面对得上，仍需实测）：
- arguments：gateway 用 `loggableArgs()`（`JSON.parse(JSON.stringify(args ?? {}))`，**无损**），
  `execute` 传的是同一份 `args` → `sameJson` 应当成立。
- callId：日志里的 `subCallId` 与 `execute({callId: subCallId})` 是同一个字符串。

**但有一个明确的破口**：`loggableArgs` 序列化失败（循环引用）时 gateway **整条事件不记**
（`meta-tools.js:139`，注释写着"宁可界面上少一张卡，也不留一条参数是假的记录"）。
真出现这种参数，auto-review 找不到 start → **按上面第 2 条抛错**，调用硬失败。
（程序里的参数来自 JSON，正常不会循环引用；属于低概率、但要记录在案的硬失败路径。）

### R3 · 并发 × 超时

- gateway 不抄官方的调度器，程序里 `Promise.all` 并发子调用是允许的；
- 每个子调用一次 review，各自一次模型请求；
- `timeoutMs` 的语义是"包含子调用与审批等待"（两边一致）—— 并发 N 个 = 同时 N 次 review，
  谁先回来不确定。
- 要测：N=3/5 时的总耗时、有没有个别子调用超期、review 之间会不会串（同一 parent 下多个 subCall）。

### R4 · 提权审批与 review 的先后

- 两边的提权审批都走 `approval.approver.request()`，但 **`toolName` 不同**：
  官方报 `run_code`，gateway 报 `call_tools`。任何**按工具名**配置的审批策略都会看出差别。
- Auto 模式会强制把审批策略设成 `ask`（README 第 46 行），所以提权审批确实会弹给人。
- 要测：**先被 review 拒 → 程序拿到异常 → 再申请提权**这条链上，审批弹窗出现几次、顺序如何。

### R5 · 拒绝在程序里的表现

- gateway 的子调用抛错会进到程序的 `catch`；被 catch 住之后外层 `call_tools` **正常返回**。
- 要测：错误文本是不是 auto-review 那两句（`Auto review rejected tool "<name>"; its body was not executed`），
  以及它在 `call_tools` 的返回值 / 日志 `tool/ptc-dispatch` 里长什么样。

### R6 · 外层 transport 不被审，会不会被"绕过"

官方**刻意**不审外层 `run_code`（它是 transport，不是效果）。gateway 的 `call_tools` 是一等工具，
所以它有"自己的"审查。这在语义上没有漏洞，但带来一个反直觉的结果：
**同一个程序，走官方 PTC 时"程序体本身"没被审，走工具箱时被审了一次。**
要确认这是否会让某些动作被多拒一次。
